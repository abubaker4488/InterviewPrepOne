  Q: "Describe a time you led an integration effort with a major ERP system (like SAP). What challenges did you face?"

  - T: I owned the development of the inbound API layer to consume, validate, map, and persist SAP-BRIM data into MBS, ensuring zero

    - Wrote comprehensive contracts (Swagger/OpenAPI) and integration tests (using WireMock for SAP simulator).

  - R: Migration went live with <0.1% defect rate (vs. historical 5%+ for similar cuts). Reduced data reconciliation effort by 70%.

  Technical Follow-Ups:
  Q: "How did you handle data mapping between SAP IDocs and your internal model?"
  A:

  - Created IDoc-specific DTOs matching SAP's XML structure (generated from SAP-provided XSDs via JAXB).

      @Mapping(target = "productCode", source = "E1KTMLL.MATNR")

      @Mapping(target = "subscriptions", source = "E1KTMLL")

  Q: "How did you ensure data consistency during the SAP cutover?"
  A:
  - Implemented a dual-write phase for 2 weeks pre-cutover:
    - Legacy systems continued writing to MBS via old APIs.
    - SAP-BRIM also wrote to MBS via our new inbound API.
    - We ran a reconciliation job (every 15 mins) comparing:
  -- Legacy vs. SAP write counts for same customer/product/time window
  SELECT legacy.customer_id, sap.customer_id,
         COUNT(*) AS legacy_count,
         (SELECT COUNT(*) FROM sap_writes WHERE ...) AS sap_count
  FROM legacy_writes legacy
  WHERE legacy.write_time BETWEEN ? AND ?
  GROUP BY legacy.customer_id
  HAVING legacy_count != sap_count;
    - Any mismatch triggered an alert for investigation.

  - Cutover involved:
    a. Freezing legacy writes at T-0.
    b. Flushing SAP backlog (processed via our API with idempotency checks).
    c. Switching MBS to read-only from SAP-only.

  - Used database locks (SELECT FOR UPDATE) on customer records during persistence to prevent concurrent legacy/SAP writes during
  transition.
  Key Points to Mention: Dual-write minimized risk; reconciliation caught 3 mapping bugs pre-cutover; DB locks prevented split-brain
  scenarios during transition window (only held for <200ms per customer).

  SECTION 3: ATC EDIT-FLOW REFACTOR

  (Consolidated fragmented multi-API edit operations)

  Q: "Tell me about a time you refactored a brittle API surface to improve maintainability."
  A (STAR):
  - S: The ATC (Account & Teams Configuration) edit-flow had 12+ disjointed REST APIs (e.g., /api/atc/user/{id}/role,
  /api/atc/user/{id}/department, /api/atc/user/{id}/contact) managed by different teams. This caused:
    - Inconsistent validation (some APIs checked permissions, others didn't).
    - Partial-update risks (e.g., updating role without department could leave invalid state).
    - High cognitive load for frontend teams (React SPA needing to call 5 APIs for one user edit).

  - T: I was assigned to consolidate these into a single, cohesive backend pattern reducing errors and improving long-term
  maintainability.
  - A:
    - Designed a single canonical endpoint: PATCH /api/v2/atc/customers/{customerId} with a JSON Patch (RFC 6902) request body.
    - Created an ATC Customer Aggregate domain object representing the full editable state (roles, departments, contacts,
  subscriptions).
    - Built a validation pipeline using Spring Validator:
        i. JSON Syntax Validation (Jackson).
      ii. Semantic Validation (e.g., "role X requires department Y").
      iii. Business Rule Validation (e.g., "cannot delete last admin role").

    - Used optimistic locking (@Version) to prevent lost updates.
    - Implemented audit logging (Envers) capturing who changed what and when.
    - Provided backward compatibility via a facade layer translating legacy API calls to the new PATCH endpoint (deprecated over 6
  months).

  - R: Reduced partial-update errors by 85%. Decreased frontend API calls per edit from 4.7→1.2. Cut new feature development time by
  40% (adding a new editable field now requires one validation rule, not 5 API changes).

  Technical Follow-Ups:
  Q: "How did you handle validation logic for interdependent fields (e.g., role requires department)?"
  A:
  - Used Spring's Validator interface with @Autowired dependencies to access reference data (e.g., RoleDepartmentRuleService).
  - Built composite validators for complex rules:
  @Component
  public class AtcCustomerValidator implements Validator {

      private final RoleDepartmentRuleService roleDeptService;

      @Override
      public boolean supports(Class<?> clazz) {
          return AtcCustomerPatch.class.isAssignableFrom(clazz);
      }

      @Override
      public void validate(Object target, Errors errors) {
          AtcCustomerPatch patch = (AtcCustomerPatch) target;

          // Check each operation in the JSON Patch
          for (Operation op : patch.getOperations()) {
              if ("add".equals(op.getOp()) || "replace".equals(op.getOp())) {
                  String path = op.getPath(); // e.g., "/roles/0/name"

                  if (path.startsWith("/roles/")) {
                      String roleId = extractRoleIdFromPath(path);
                      Object newValue = op.getValue(); // e.g., department ID for role

                      // Validate role-department compatibility
                      if (!roleDeptService.isValidCombination(roleId, (String) newValue)) {
                          errors.rejectValue("roles", "atc.role.dept.mismatch",
                              "Role " + roleId + " requires department " + getRequiredDept(roleId));
                      }
                  }
              }
          }
      }

      // Helper to extract ID from JSON Patch path like "/roles/123/name"
      private String extractRoleIdFromPath(String path) {
          return path.split("/")[2];
      }
  }
  Key Points to Mention: Validator ran after JSON deserialization but before service layer—caught errors early; used @Autowired to
  access reusable rule services; errors bound to specific field paths for precise frontend feedback.

  Q: "How did you ensure backward compatibility during the refactor?"
  A:
  - Created a Facade Controller (AtcLegacyFacadeController) mapping old endpoints to new PATCH logic:
  @RestController
  @RequestMapping("/api/atc/legacy")
  public class AtcLegacyFacadeController {

      private final AtcCustomerService newService; // Uses the PATCH-based logic

      @PutMapping("/user/{userId}/role/{roleId}")
      public ResponseEntity<Void> updateRoleLegacy(
          @PathVariable String userId,
          @PathVariable String roleId,
          @RequestParam String newDeptId // Legacy param

          return ResponseEntity.noContent().build();
      }

      // Similar methods for /department, /contact endpoints
  }
  - Deprecated legacy endpoints with @Deprecated and sunset headers; monitored usage via logs for 6 months before removal.
  Key Points to Mention: Facade avoided duplicating validation logic; used same service layer as new API ensuring behavioral
  consistency; gradual deprecation gave frontend teams migration time.

  SECTION 4: QUERY TIMEOUT RESOLUTION

  (Fixed Bill Preview path JPQL query)

  Q: "Describe a time you diagnosed and fixed a critical performance bottleneck in a production system."
  A (STAR):
  - S: The Bill Preview path (used by billing agents to view customer invoices before sending) timed out (>30s) during peak hours,
  affecting 200+ agents processing high-volume invoice data. This caused billing delays and agent frustration.
  - T: I owned the investigation and fix, focusing on reducing query latency while maintaining result accuracy.
  - A:
    - Used APM logs (AppDynamics) to identify the slow query: a JPQL statement fetching invoice line items with multiple joins and
  aggregates.
    - Ran EXPLAIN ANALYZE in Oracle SQL Developer revealing:
        - Full table scan on INVOICE_LINE_ITEMS (50M+ rows) due to missing index on (invoice_id, status).
      - Cartesian product caused by incorrect join condition between INVOICE and TAX_DETAILS.
      - Unnecessary DISTINCT causing costly sort operation.

    - Fixes Applied:
        - Added composite index: CREATE INDEX IDX_INV_LINE_ITEMS_INV_STATUS ON INVOICE_LINE_ITEMS (INVOICE_ID, STATUS);
      - Corrected join: FROM Invoice i JOIN i.taxDetails td ON i.id = td.invoiceId (was i.id = td.relatedId).
      - Removed DISTINCT by fixing the root cause (duplicate joins) and using GROUP BY where aggregation was truly needed.
      - Added query hint /*+ FIRST_ROWS(10) */ to optimize for first-page preview (agents rarely view >10 line items initially).

    - Validated with JMeter load test simulating 150 concurrent preview requests.

  - R: Reduced average query time from 38s to 1.2s. Eliminated timeouts entirely. Improved agent productivity by ~22% (based on
  time-saved metrics).

  Technical Follow-Ups:
  Q: "How did you identify the missing index without impacting production?"
  A:
  - Used Oracle SQL Developer's Autotrace on a staging clone of production data (refreshed nightly):
  SET AUTOTRACE EXPLAIN STATISTICS
  SELECT /*+ GATHER_PLAN_STATISTICS */
         ili.*, i.invoice_date
  FROM INVOICE_LINE_ITEMS ili
  JOIN INVOICE i ON ili.invoice_id = i.id
  WHERE i.customer_id = :custId
    AND ili.status = 'ACTIVE'
  ORDER BY ili.line_number;
  - Key metrics from DBMS_XPLAN.DISPLAY_CURSOR:
    - Before fix: Rows: 50,000,000 (full scan), Bytes: 12GB, Cost: 2,450,000
    - After index: Rows: 1,200 (index range scan), Bytes: 288KB, Cost: 85

  - Confirmed in production via AWR report showing decreased db file sequential read waits for the query's SQL ID.
  Key Points to Mention: Never tested indexes directly in production; used staging with realistic data volume; validated with both
  explain plan and actual execution stats.

  Q: "Why did you choose a composite index over two single-column indexes?"
  A:
  - The query filtered on both invoice_id (foreign key) and status (low-cardinality field: 'ACTIVE', 'CANCELLED', 'DRAFT').
  - Oracle can use index skip scan or index concatenation for multi-column predicates, but:
    - Single-column index on invoice_id would still scan all line items for an invoice (often 10-50 rows) then filter by status
  in-app—inefficient for high-status-variance invoices.
    - Single-column index on status would be useless (only 3 values—index not selective).

  - Composite index (invoice_id, status) allowed Oracle to:
    a. Quickly locate the invoice_id range (using leading column).
    b. Within that range, filter by status using the second column (no table access needed for filtering).

  - Verified via EXPLAIN PLAN showing INDEX RANGE SCAN IDX_INV_LINE_ITEMS_INV_STATUS instead of TABLE ACCESS FULL.
  Key Points to Mention: Chose column order based on selectivity (high-cardinality invoice_id first); composite index served both
  filtering and join optimization (used in join condition too).

  SECTION 5: SECURITY HARDENING

  (Prevented log injection attacks)

  Q: "Tell me about a time you identified and fixed a security vulnerability in a customer-facing system."
  A (STAR):
  - S: During a routine code review, I discovered that user-supplied input (e.g., customer names, addresses) was being logged
  directly via log.info("Processing customer: " + customerName) in several Spring MVC controllers. This created a log injection
  vulnerability where attackers could inject newlines or control characters to forge log entries (e.g., mimicking successful login
  attempts).
  - T: I led the effort to sanitize all customer-facing input logging across the MBS billing portal (JSP) and REST API endpoints
  within 2 weeks, coordinating with the security team.
  - A:
    - Created a centralized LogSanitizer utility using Oracle's AXS (Application Security) guidelines:
        - Replaced newlines (\r, \n) with \\n.
      - Escaped control characters (ASCII 0-31, 127) as \xHH.
      - Limited string length to 500 chars to prevent DoS via massive logs.
      - Preserved UTF-8 validity (did not break multi-byte sequences).

    - Applied sanitization at the logging point (not input validation) to:
        - Preserve original data for audit/db storage.
      - Avoid double-sanitization bugs.
      - Cover all logging frameworks (Logback, Log4j2, System.out).

    - Updated all controllers (REST + JSP servlets) to use:
  logger.info("Processing customer: {}", LogSanitizer.safeLog(customerName));
    - (Never used string concatenation for logging—always used parameterized logging).
    - Added SonarQube rule (squid:S2077) to block logger.info("msg " + var) patterns in customer-facing modules.
    - Conducted brown-bag session for 15 developers on secure logging practices.

  - R: Eliminated log injection vulnerability (confirmed by pen test). Zero security findings related to logging in subsequent
  audits. Improved log utility for debugging (cleaner, parseable logs).

  Technical Follow-Ups:
  Q: "Why sanitize at logging time instead of input validation?"
  A:
  - Input validation should enforce business rules (e.g., "name must be 2-50 chars, alphanumeric + spaces").
  - Log injection is a logging infrastructure issue—we needed to preserve the actual user input for:
    - Audit trails (legal requirement for billing systems).
    - Debugging reproduction issues (e.g., a customer name with embedded newline caused a parsing bug in legacy report).
    - Downstream systems consuming logs (ELK, Splunk) expecting raw data.

  - Sanitizing at logging time:
    - Keeps source of truth intact (DB/audit logs).
    - Applies uniformly to all logging (including framework-generated logs we don't control).
    - Avoids TOCTOU bugs (input validated, then altered before logging).
  Key Points to Mention: Separation of concerns—validation for business logic, sanitization for output safety; cited OWASPASVS
  v4.0.3: "Output encoding must be applied based on the context where the data is used."

  Q: "Show me the LogSanitizer implementation."
  A:
  public final class LogSanitizer {
      private LogSanitizer() {} // Prevent instantiation

      // Preserves UTF-8, escapes control chars & newlines, limits length
      public static String safeLog(String input) {
          if (input == null) return "null";
          if (input.isEmpty()) return "";

          // Fast path for common safe strings (alphanumeric + basic punctuation)
          if (input.matches("^[\\p{L}\\p{N}\\s\\-_.@,:#]+$") && input.length() <= 500) {
              return input;
          }

          StringBuilder sb = new StringBuilder(Math.min(input.length(), 500));
          int codePointCount = 0;

          for (int i = 0; i < input.length(); ) {
              int cp = input.codePointAt(i);
              int charCount = Character.charCount(cp);

              // Skip if over length limit (preserves UTF-8 by not splitting surrogates)
              if (codePointCount++ >= 500) {
                  sb.append("...[TRUNCATED]");
                  break;
              }

              // Handle control characters and del
              if (cp < 0x20 || cp == 0x7F) {
                  sb.append(String.format("\\x%02X", cp));
              }
              // Handle newline/carriage return explicitly (common attack vector)
              else if (cp == '\n' || cp == '\r') {
                  sb.append('\\').append((char) cp);
              }
              // All other chars (including UTF-8 multibyte) added as-is
              else {
                  sb.appendCodePoint(cp);
              }

              i += charCount;
          }
          return sb.toString();
      }
  }
  Key Points to Mention: Handled surrogate pairs correctly (UTF-8 safety); used early-exit for ASCII strings (common case); length
  limit prevents log flooding; avoidance of regex in hot path for performance; validated with OWASP's log injection test vectors.

  Q: "How did you handle database schema changes across the ecosystem?"
  A:
  - Used Flyway for version-controlled, repeatable migrations:

  Q: "Why did you choose GitHub Actions over Jenkins for CI/CD?"

    - Simpler YAML: Declarative pipelines vs. Jenkins' Groovy DSL (lower learning curve for new team members).

  - We did not migrate existing Jenkins pipelines for stable apps (like the JSP portal) unless refactoring—avoided churn for minimal

  Key Points to Mention: Pragmatic adoption—used Actions for new/greenfield work; kept Jenkins for brownfield apps where migration
  cost > benefit; cited specific pain points (Groovy complexity, credential management).

  A (Lumen Context):

  *Q: "How does ConcurrentHashMap achieve better thread-safety than Hashtable?"
  A (Lumen Context):
  - In the SAP-BRIM inbound API, we used ConcurrentHashMap to cache recently validated IDoc schemas (XSDs) to avoid reparsing on
  every request.
  - Hashtable would lock the entire map for every get()/put(), creating contention under load (we saw 500+ req/min spikes).
  - ConcurrentHashMap uses segment-level locking (or in Java 8+, CAS + bins) so:
    - Multiple threads can read different segments simultaneously.
    - Writes only lock the specific segment being modified.

  - This gave us ~8x better throughput under peak load (validated via JMeter).
  - Key Insight: Choose synchronization granularity based on access patterns—our cache had high read/write ratio with key-based
  locality.

  *Q: "How would you design a Kubernetes deployment for a high-traffic payment API?"
  A (Lumen Context - Adapted from MBS REST API):
  - Based on our MBS REST API deployment (handling ~2K RPM peak):
    - Resource Requests/Limits:
  resources:
    requests:
      memory: "512Mi"
      cpu: "250m"
    limits:
      memory: "1Gi"
      cpu: "500m"
        - Requests set based on average usage (from Prometheus); limits set to 2x requests to allow burst without OOMKill.

    - Readiness/Liveness Probes:
  readinessProbe:
    httpGet:
      path: /actuator/health
      port: 8080
    initialDelaySeconds: 10
    periodSeconds: 5
  livenessProbe:
    httpGet:
      path: /actuator/health/liveness
      port: 8080
    initialDelaySeconds: 60
    periodSeconds: 10
        - Readiness: checks if app can serve traffic (DB connections up, Kafka consumers alive).
      - Liveness: checks for fatal JVM issues (deadlock, OOM) - slower to avoid false positives.

    - Horizontal Pod Autoscaler (HPA):
  apiVersion: autoscaling/v2
  kind: HorizontalPodAutoscaler
  metadata:
    name: mbs-api-hpa
  spec:
    scaleTargetRef:
      apiVersion: apps/v1
      kind: Deployment
      name: mbs-api
    minReplicas: 3
    maxReplicas: 15
    metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60
        - Targeted 60% CPU utilization (left headroom for GC spikes); min 3 replicas for AZ resilience.

    - Key Insight: Always set resource requests—Kubernetes scheduler uses them for node placement; without requests, pods get
  best-effort QoS and are first to be killed under pressure.
