# MBS Billing Platform — Complete System Analysis

---

## A. Executive Summary

**MBS (Managed Billing System)** is an enterprise-grade billing platform built for **Lumen Technologies** (formerly CenturyLink/CTL), a major US telecom provider. It handles the full lifecycle of telecom billing: customer setup, bill generation, tax computation, invoice delivery, payment posting, and financial reconciliation. The platform serves multiple sub-systems (called "system names" — e.g., `BARTMBS`) and supports tens to potentially hundreds of enterprise customers.

The system is composed of four interconnected applications that share an Oracle database:

| App | Role |
|---|---|
| **mbs-app-API** | Core billing engine — exposes REST APIs for all billing operations |
| **mbs-app-GUI** | Legacy web UI — JSP-based interface for billing agents and admins |
| **ATC** | Modern project management UI — React SPA managing construction billing projects |
| **mbs-app-BATCH** | Batch engine — standalone Java library for billing computation and invoice generation |

## 1. mbs-app-API — Deep Analysis

### 1.1 High-Level Purpose
The core REST API backend for the entire MBS billing platform. It is the single source of truth for billing logic. Both the GUI and ATC consume it.

### 1.2 Business Purpose
- Automates telecom billing: rate customers, compute taxes, generate invoices, post payments, apply adjustments
- Integrates with external financial systems (BRIM) for journal entries, accruals, and write-offs
- Provides PDF invoice generation on demand
- Enables the batch billing cycle to be triggered via REST endpoints

### 1.3 Technology Stack

| Component | Technology |
|---|---|
| Framework | Spring Boot 2.5.6 |
| Language | Java 8 |
| Database | Oracle (ojdbc8), JPA/Hibernate |
| Packaging | WAR deployed to Tomcat |
| Docs | Springdoc OpenAPI / Swagger UI |
| PDF | iText 7 |
| Email | Spring Boot Mail |
| HTTP client | Apache HttpClient |
| Batch engine | `MbsBatch-1.0.jar` (mbs-app-BATCH embedded as dependency) |
| Serialization | Jackson 2.12 |

### 1.4 Architecture Overview
- Follows layered Spring MVC: `Controller → Service/Repository → Model → Oracle DB`
- **`MbsBillingDef`** (from the Batch JAR) is the core computation engine, called directly from `CustomerBillingController`
- **BRIM** integration layer (dedicated `brim/` package) handles all external financial system communication
- Multi-environment support via commented `application.properties` blocks: DEV, TEST, TEST2, PREPROD, BRSPD, PROD

### 1.5 Major Controllers and Their Business Roles

| Controller | Endpoint(s) | Business Role |
|---|---|---|
| `CustomerController` | `/customer`, `/getCustomerId`, `/downloadBill` | Customer CRUD, bill download |
| `CustomerBillingController` | `/customerBilling`, `/generatebillPreviewPdf` | Run billing for a customer, preview PDF invoice |
| `BatchInvoiceController` | `/batch-invoice/process-complete-invoice`, `/batch-invoice/*` | Orchestrate full invoice workflow: rating → billing → taxing → formatting |
| `AdjustmentController` | `/cancelInvoice` | Invoice cancellation, credit adjustments |
| `PostPaymentController` | `/postPayment` | Post incoming payments, update bill balance history |
| `MbsBrimFileController` | `/MbsBrimFileDetails`, `/MbsBrimAccrualsDetails`, `/setOutboundJson`, etc. | BRIM integration: charges, accruals, payments, write-offs, daily feed |
| `MbsTaxController` | `/Cgs-AccesToken`, `/Cgs-prod-AccesToken` | CGS/Vertex tax engine authentication |
| `MnetController` | `/AssignDetails`, `/DeligationDetails`, `/DeligationStatus` | Employee directory lookups and delegation chains for approval workflows |
| `DataMappingController` | (data mapping) | Product/service code cross-reference management |
| `AppPropertiesController` | (config) | Runtime application configuration |

### 1.6 Key Models (Entities)

| Entity | Business Meaning |
|---|---|
| `CustomerDetail` | Master customer record with billing address, system name |
| `BillInvoiceDetails` | Individual invoice header record |
| `BillComputeDetail` | Line-level charge breakdown per service code |
| `TaxComputeDetail` | Tax calculation result per invoice line |
| `BillAdjustments` | Credit/debit adjustments against invoices |
| `BillBalHistory` | Running balance history — paid/pending amounts |
| `PaymentDetails` | Individual payment transaction record |
| `ProductServiceRate` | Rate table for telecom products/services |
| `MBSBillPullDetail` | Billing cycle control — tracks bill pull dates per customer |
| `MbsBrimTax` | Tax data for BRIM reconciliation |
| `AssignDetails` | Approval assignment rules (amount thresholds per user) |
| `ErrorLog` | Billing process error tracking |
| `OutboundJson` / `InboundJson` | BRIM integration message queue records |
| `LegacyProductXref` | Cross-reference between legacy system product codes and MBS codes |

### 1.7 BRIM Integration (Critical)
**BRIM = Billing and Revenue Management** — an external financial system (likely SAP or similar ERP).

MBS sends BRIM:
- **Charges** — billed amounts per customer per period
- **Accruals** — projected revenue before billing
- **Payment transactions** — received payments
- **Write-off transactions** — uncollectible amounts
- **Daily feed** — account history, payment history, write-off history

The `MbsBrimDailyFeedServiceImpl` calls BRIM via HTTP using Basic Auth, posting JSON request DTOs and receiving structured response DTOs.

### 1.8 Important Workflows

**Invoice Generation Workflow** (`/batch-invoice/process-complete-invoice`):
```
1. Validate system name
2. Rating: calculateUsageAndOCCCharges (RatingService)
3. Billing: processBillingForCustomerList (BatchBillingInvoiceService)
4. Taxing: computeTaxes (BatchTaxingInvoiceService)
5. Formatting: formatInvoices, generate PDF (BatchFormattingInvoiceService)
```

**Payment Posting Workflow** (`/postPayment`):
```
1. Validate customer exists
2. Record PaymentDetails
3. Update BillBalHistory (PAID status)
4. Update BillInvoiceDetails
5. Send to BRIM via outbound JSON
```

**Invoice Cancellation** (`/cancelInvoice`):
```
1. Validate invoice exists
2. Create reversal BillAdjustments with ADJ prefix
3. Update BillBalHistory
4. Log to ErrorLog if needed
```

## 2. mbs-app-BATCH — Deep Analysis

### 2.1 High-Level Purpose
A standalone Java library (compiled as a JAR) containing the core billing computation engine. It is **not a web application** — it is embedded directly into `mbs-app-API` as a Maven dependency (`MbsBatch-1.0`).

### 2.2 Business Purpose
- Performs the actual mathematical billing computation
- Generates formatted invoice files (PDF, text)
- Handles usage rating, OCC (One-Time Charges), expense billing, PIU (Percent in Use) splitting
- Calculates taxes via the CGS/Vertex tax engine
- Creates invoice files for delivery to customers

### 2.3 Technology Stack

| Component | Technology |
|---|---|
| Language | Java 8 |
| ORM | Hibernate (direct Session/Transaction — not Spring) |
| PDF | Custom PDF formatter with embedded fonts |
| Email | JavaMail |
| Logging | Log4j |
| DB | Oracle via JDBC |
| Packaging | JAR library |

> **Critical design note**: The Batch module uses **raw Hibernate sessions** (not Spring Data JPA). It directly manages `Session` and `Transaction` objects. This is legacy architecture from before the Spring Boot migration.

### 2.4 Major Service Classes

| Class | Business Role |
|---|---|
| `MbsBillingDef` | **Master orchestrator** — calls all sub-processes in order |
| `MbsBillingAndCreateInvoices` | Drives the billing computation and invoice creation |
| `MbsRatingProcess` / `MbsUsageRatingProcess` | Rate usage records against product/service rate tables |
| `MbsTaxCalcAndFrmt` / `MbsTaxComputeNewCalc` | Tax calculation using CGS/Vertex |
| `MbsOccChargesCalc` | One-time charge computation |
| `MbsPIUSplitCalc` / `MbsPIUSplitCalcMonthly` | Percent-in-use splits for shared services |
| `MbsConstructCompute` | Builds the compute detail objects |
| `MbsPdfFormatNewDP` / `MbsPdfFrmtPart1` | PDF invoice formatting |
| `MbsInvoiceCreateWriteDP` | Writes invoice files to disk |
| `MbsBillBalHistoryInsert` | Inserts balance history after billing |
| `MbsPaymentAutoIns` | Auto-inserts payment records in certain scenarios |
| `MbsStatementProcessor` | Statement/summary generation |
| `AtxATTFileRecordsDP` | AT&T format file processing |
| `BillReRunProcess` | Re-run billing for a prior period |

### 2.5 Environment Setup
`MbsEnvSetup` defines environments: `DEV, TEST, TEST2, PREPROD, BRSPD, PROD`. All DB connection strings, email recipients, API endpoints, and file paths are controlled by this single enum switch. The Batch module reads property files (`api-DEV.properties`, `hibernate-DEV.properties`, etc.) from the `bin/` or `src/` directory.

## 4. ATC — Deep Analysis

### 4.1 High-Level Purpose
A modern React + Spring Boot application managing the **Access Termination Charge (ATC)** billing project lifecycle — specifically for construction/infrastructure projects billed to external customers (highway relocates, special construction, MDU, etc.).

### 4.2 Business Purpose
- Engineers submit new billing projects with WBS elements, cost details, customer info
- Finance team reviews proposals, sends payment request URLs, records PO/check payments
- System generates PDF proposals using Adobe Sign / PDF templates
- Tracks project status through a state machine workflow
- Automatically polls MBS API and BRIM for payment status on eligible projects
- Sends emails at key workflow transitions
- Generates addendums (project scope changes)

### 4.3 Technology Stack

| Component | Technology |

| Backend | Spring Boot 3.2.2, Java 17 |
| Frontend | React 18, React Router 6, Axios |
| Database | Oracle (ojdbc11 21.9) |

## C. End-to-End Request Flows

### Flow 1: Billing Agent Posts a Payment (GUI → API → Oracle)
```
1. Agent opens PaymentPage.jsp in mbs-app-GUI
2. GUI controller calls mbs-app-API /postPayment via RestTemplate
3. API PostPaymentController validates customer in CustomerDetail table
4. API inserts PaymentDetails record (Oracle)
5. API updates BillBalHistory to PAID status
6. API updates BillInvoiceDetails
7. API queues outbound BRIM JSON via OutboundJsonRepository
8. BRIM picks up JSON and confirms payment in revenue management
9. GUI shows confirmation back to agent
```

### Flow 2: Full Invoice Generation (API BatchInvoiceController)
```
1. POST /batch-invoice/process-complete-invoice?systemName=BARTMBS&billPullDate=23-MAY-25
2. Validate systemName
3. RatingService: rate all usage records for customer list
4. BatchBillingInvoiceService: MbsBillingDef.BillingInfo() → full billing computation
   - Pulls bill pull dates, customer config
   - Computes line charges per service code
   - Handles OCC, PIU splits, expense billing
   - Inserts BillComputeDetail, BillInvoiceDetails
5. BatchTaxingInvoiceService: calls CGS/Vertex API for tax amounts
   - Inserts TaxComputeDetail
6. BatchFormattingInvoiceService: generates PDF invoice
   - Writes to file system + stores as base64 in BillInvFile
7. Returns success/failure response
```

### Flow 3: ATC Project Payment Tracking (Scheduled)
```
2:30 AM daily — MBSPaymentHistoryScheduler fires
1. Reads APP_PROPERTIES for "EligibleStatusForMBSPmtInfoCheck" statuses
2. Queries PROJECT_DATA for projects in those statuses
3. For each project: calls MBSServiceAdaptor → mbs-app-API /customerPaymentHistory
4. If payment found: inserts Payment record in ATC Oracle schema
5. Calls WorkflowTransitionService → updates project status
6. Sends email notification to originator
```

## G. Interview Cheat Sheet

### Q: What is MBS?
> MBS is Lumen's internal telecom billing platform. It takes usage data for enterprise customers, rates it against product service rate tables, computes state and federal taxes using the Vertex/CGS engine, generates PDF invoices, posts payments, sends accruals and charges to the BRIM revenue management system, and provides web UIs for billing agents and project managers.

### Q: How does the billing process work end to end?
> A POST request to `/batch-invoice/process-complete-invoice` triggers a four-step pipeline: (1) Rating — usage records are rated against rate tables; (2) Billing — `MbsBillingDef` computes all charges, OCC, and PIU splits and writes to BillComputeDetail; (3) Taxing — the CGS/Vertex API calculates telecom-specific taxes; (4) Formatting — a PDF invoice is generated using iText and stored. Results flow into the Oracle BILL_INVOICE_DETAILS and related tables.

### Q: What is BRIM and how does MBS interact with it?
> BRIM is Lumen's Billing and Revenue Management system — essentially the financial system of record. MBS sends BRIM structured JSON payloads containing charges, accruals, payment transactions, and write-offs via authenticated REST calls. MBS also polls BRIM's daily feed endpoints for payment history and account history to keep billing records synchronized.

### Q: What is ATC?
> ATC stands for Access Termination Charge. It's a React + Spring Boot application that manages construction-related billing projects (highway relocates, special construction, line extensions) through a defined workflow: Engineer submits → Finance reviews → Payment URL sent to customer → PO received → Billing data sent to MBS → Payment confirmed. Automated schedulers poll MBS and BRIM nightly to detect when payments arrive.

### Q: How does the GUI communicate with the API?
> The GUI is a Spring Boot application with server-side JSP rendering. Its `@Controller` classes use a `RestTemplate`-based `RestClient` helper to make HTTP calls to `mbs-app-API`. The GUI itself does not directly access the Oracle billing tables for read/write operations — it delegates to the API layer.

### Q: What database does the system use and why Oracle?
> Oracle Database is used across all applications. Specific connection strings show TNS names pointing to `azeus2lorambsn1.corp.intranet` for cloud-hosted instances and `racorad`-prefixed hosts for on-premises RAC clusters. Oracle was chosen for its enterprise reliability, RAC (Real Application Clusters) for high availability, and its support for complex billing-grade queries.

### Q: How is tax computation done?
> MBS integrates with CGS (likely Vertex Communications Tax Engine) for all tax calculations. The API first obtains an OAuth access token via `/Cgs-AccesToken`, then passes billing line items to the tax API. Results are stored in `TaxComputeDetail` and linked to invoices. The Batch module also has `MbsTaxComputeNewCalc` and `MbsTaxCalcAndFrmt` for batch tax processing.

### Q: How does approval delegation work?
> The `MnetController` exposes endpoints that query the `AssignDetails` table. When a user submits an action (e.g., large payment), the system calls `/AssignDetails?cuid=X&amount=Y&systemName=Z` to look up who in the org hierarchy has approval authority for that dollar amount. Delegation is handled by `/DeligationDetails` and `/DeligationStatus`.

### Q: What are the different environments?
> DEV, TEST, TEST2, PREPROD, BRSPD (BRSP Pre-prod), and PROD. Each maps to a different Oracle database instance and connection string. The Batch module uses property files (`api-DEV.properties`, `hibernate-DEV.properties`) per environment. The API uses commented blocks in `application.properties`.

### Q: What is PIU (Percent in Use)?
> PIU is a billing concept for shared telecom facilities. If a service is used by multiple customers (e.g., a shared fiber span), the cost is split proportionally. `MbsPIUSplitCalc` and `MbsPIUSplitCalcMonthly` compute these splits and allocate charges across customers accordingly.

### Q: How does PDF invoice generation work?
> The Batch module's `MbsPdfFormatNewDP` and `MbsPdfFrmtPart1` build PDFs programmatically using iText with embedded custom fonts (`courier-new-bold.ttf`). The PDF is written to a file system path and also encoded as base64 bytes returned via the API. In the GUI, `BCPdfBillService` handles viewing existing stored PDF bills.
